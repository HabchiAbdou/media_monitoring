\section{Introduction \& contexte}
Le projet \emph{media\_monitoring} fournit une chaîne de veille médiatique centrée sur OCP, du recueil de mentions jusqu'aux exports PDF/CSV. Le code backend est basé sur Django (\texttt{monitoring/}), le frontend interne sur templates HTML/CSS (\texttt{monitoring/templates/}) avec un prototype Vite/React (\texttt{FrontEnd\_extracted/src/}). Les rapports sont rendus via \texttt{xhtml2pdf} à partir de gabarits HTML (\texttt{report\_pdf.html}). Les données sont persistées en SQLite en développement, et l'application est prévue pour un déploiement sur Render.

\subsection{Positionnement}
Le produit cible les équipes communication et gestion de risque d'OCP. Il offre des alertes urgentes, une vue agrégée des sources, et des rapports exportables pour diffusion interne ou gouvernance.

\subsection{Public visé de ce rapport}
Ce document s'adresse à un public technique (ingénieurs data, backend, ops) et produit en français. Les termes techniques usuels (backend, frontend, pipeline, database, API, deployment, Render, queue, worker, endpoint, ORM, UI, component, state, etc.) sont conservés en anglais lorsqu'ils sont standard.

\section{Objectifs du projet et périmètre}
\subsection{Objectifs}
\begin{itemize}[leftmargin=1.2cm]
    \item Centraliser et classifier les mentions d'OCP provenant de sources web variées.
    \item Détecter le sentiment et les signaux d'alerte (\texttt{is\_urgent}) via un LLM interne.
    \item Offrir un tableau de bord temps quasi-réel et des exports structurés (PDF, CSV).
    \item Garantir la traçabilité (horodatage, provenance, sortie LLM) et la reproductibilité.
\end{itemize}

\subsection{Hors périmètre}
Le scraping détaillé (choix des librairies, parsing) est géré par un autre membre de l'équipe et n'est pas documenté ici. On mentionne uniquement son rôle et ses entrées/sorties.

\section{Pipeline de bout en bout}
\subsection{Chaîne principale}
\begin{enumerate}[leftmargin=1.2cm]
    \item \textbf{Déclenchement} : bouton ``Lancer la veille'' (dashboard) ou POST \texttt{/run-monitor/}.
    \item \textbf{Scraping} (haute vue) : récupère les cibles \texttt{ScrapeTarget}, collecte les pages et renvoie texte + méta ; géré par un autre membre.
    \item \textbf{Nettoyage} : suppression balises, squelettes de template.
    \item \textbf{LLM} : prompt JSON (sentiment, scores, raisons, résumé, risque, recommandations) puis interprétation structurée.
    \item \textbf{Persistance} : enregistrement \texttt{Mention} avec indicateur d'urgence et méta LLM.
    \item \textbf{Consultation} : dashboard, API \texttt{/api/mentions}, \texttt{/api/alerts}.
    \item \textbf{Rapport} : agrégation et export PDF/CSV via \texttt{report\_view}.
\end{enumerate}

\section{Profils et rôles (admin vs utilisateur)}
\subsection{Profil administrateur}
\begin{itemize}[leftmargin=1.2cm]
    \item Accès via routes d'administration (\texttt{/administration/login/}, \texttt{/administration/users/}, \texttt{/administration/scrape-targets/}).
    \item Peut créer/désactiver/supprimer des utilisateurs, réinitialiser leurs mots de passe, et gérer les \texttt{ScrapeTarget} (activer/désactiver, ajouter, supprimer).
    \item Accès aux mêmes vues que l'utilisateur standard (dashboard, rapports) mais avec navigation Admin visible.
    \item Authentification stricte : seuls les superusers (Django) passent les gardes \texttt{admin\_required}.
\end{itemize}

\subsection{Profil utilisateur standard}
\begin{itemize}[leftmargin=1.2cm]
    \item Accès au dashboard (\texttt{/}) pour voir les mentions, urgences, stats et lancer la veille (\texttt{/run-monitor/}).
    \item Accès à la page Rapports (\texttt{/report/}) pour générer et télécharger PDF/CSV; visualisation HTML (\texttt{format=view}) accessible.
    \item Pas d'accès aux routes d'administration ni à la gestion des comptes ou des cibles de scraping.
    \item Authentifié via les vues de login standard Django (\texttt{/accounts/login/}) et soumis aux permissions \texttt{login\_required}.
\end{itemize}

\section{Génération de rapports (section majeure)}
\subsection{Formats produits}
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{PDF} : rendu HTML $\rightarrow$ PDF via \texttt{xhtml2pdf} (\texttt{render\_report\_pdf}), polices Noto pour le multilingue.
    \item \textbf{CSV} : export tabulaire (\texttt{render\_report\_csv}) avec en-tête fixe : id, date, source\_name, source\_type, title, url, sentiment, category.
    \item \textbf{HTML interne} : \texttt{report\_view.html} pour lecture directe des mêmes données.
\end{itemize}

\subsection{Chaîne de bout en bout}
\begin{enumerate}[leftmargin=1.2cm]
    \item \textbf{UI trigger} : bouton \texttt{Generate PDF} ou \texttt{Download CSV} (\texttt{report.html}); POST \texttt{/report/} avec \texttt{format} et \texttt{source\_id} (optionnel).
    \item \textbf{Requête backend} : \texttt{report\_view} lit les paramètres, appelle \texttt{build\_ocp\_report\_data(source\_id)}.
    \item \textbf{Database query} : \texttt{get\_ocp\_mentions\_queryset} filtre sur company OCP (ou fallback mot-clé), applique \texttt{source\_id} si fourni.
    \item \textbf{Transformation/agrégation} :
    \begin{itemize}[leftmargin=0.9cm]
        \item Calcul KPI : \texttt{total\_mentions}, \texttt{mentions\_this\_month}, \texttt{mentions\_by\_source\_type}, \texttt{sentiment\_counts}.
        \item Normalisation des labels (positif/négatif/neutre), scores (\%), niveaux de risque, recommandations, raisons du sentiment.
        \item Extraits (\texttt{\_pick\_excerpt}), résumés (\texttt{\_clean\_summary\_text}), catégorie (\texttt{\_resolve\_category}).
    \end{itemize}
    \item \textbf{Mise en forme} :
    \begin{itemize}[leftmargin=0.9cm]
        \item Injection dans \texttt{report\_pdf.html} avec sections Synthèse, KPIs, Mentions détaillées.
        \item CSS embarqué (polices, couleurs, bordures) pour un rendu stable en PDF.
    \end{itemize}
    \item \textbf{Fichier} : \texttt{pisa.CreatePDF} produit un flux en mémoire; nommage \texttt{rapport\_ocp\_\{timestamp\}.pdf}. CSV similaire.
    \item \textbf{Download} : réponse HTTP avec \texttt{Content-Disposition: attachment}; pas de stockage disque persistant.
\end{enumerate}

\subsection{Filtres et paramètres}
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{Source} : \texttt{source\_id} limite le queryset; exposé dans \texttt{report.html} par ligne de source.
    \item \textbf{Fenêtre temporelle implicite} : \texttt{Min/Max} sur \texttt{published\_at} pour afficher la période couverte; calcul \texttt{mentions\_this\_month}.
    \item \textbf{Mots-clés/catégories} : non filtrables en UI, mais présents en sortie (colonne catégorie, raisons du sentiment).
\end{itemize}

\subsection{Gestion des erreurs}
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{Dataset vide} : PDF affiche ``Aucune mention disponible''; CSV contient uniquement l'en-tête.
    \item \textbf{Paramètres invalides} : format non reconnu $\rightarrow$ fallback PDF; \texttt{source\_id} inexistant $\rightarrow$ ignoré.
    \item \textbf{PDF partiellement rendu} : erreurs \texttt{pisa} logguées mais la réponse est renvoyée (meilleure expérience utilisateur).
\end{itemize}

\subsection{Traçabilité}
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{Horodatage} : \texttt{generated\_at} et période couverte en tête de rapport.
    \item \textbf{Provenance} : \texttt{source\_name}, \texttt{source\_type}, \texttt{original\_url} par mention.
    \item \textbf{Méta LLM} : \texttt{raw\_metadata.llm.input/output/structured} conservés pour audit.
    \item \textbf{Reproductibilité} : normalisation des labels et scores assure des distributions cohérentes.
\end{itemize}

\subsection{Scalabilité}
\begin{itemize}[leftmargin=1.2cm]
    \item \textbf{Grand volume} : PDF construit en mémoire; prévoir pagination ou limitation de mentions pour éviter la surcharge.
    \item \textbf{Async} : ajout recommandé d'une \textbf{queue + worker} (Celery/RQ) pour générations lourdes ou multiples.
    \item \textbf{Cache} : mettre en cache les KPI par source (time-box) pour ne pas recalculer CSV/PDF séquentiels.
    \item \textbf{Stockage objet} : optionnel pour conserver un historique (Render/Cloud bucket) au lieu d'un flux éphémère.
\end{itemize}

\subsection{Améliorations futures}
\begin{itemize}[leftmargin=1.2cm]
    \item Bibliothèque de \textbf{templates} (branding, couleurs, pagination).
    \item \textbf{Programmation} récurrente (journalier/hebdo) + \textbf{email delivery}.
    \item \textbf{Queue + workers} : paralléliser PDF et CSV, ajouter un statut de tâche.
    \item \textbf{Visuals} : insérer graphiques HTML/CSS (bar/pie) dans \texttt{report\_pdf.html}.
    \item \textbf{Filtres avancés} : date range, mots-clés, catégories depuis l'UI.
\end{itemize}

\subsection{Snippets essentiels (limite 2, concis)}

\section{Limitations \& travaux futurs}
\begin{itemize}[leftmargin=1.2cm]
    \item Scraping non documenté ici (géré par un autre membre).
    \item Pas de filtres date ou mots-clés en UI pour les exports.
    \item Génération synchrone (absence de queue).
    \item Auth simple (pas de MFA, pas de rate-limit API).
    \item Pas de stockage historique des rapports (flux éphémère).
\end{itemize}

\section{Conclusion}
Le projet combine un backend Django robuste, un pipeline LLM pour l'analyse de sentiment et un module de reporting PDF/CSV fiable. Les prochaines étapes clés concernent l'industrialisation Render (PostgreSQL, collectstatic), l'ajout de filtres avancés pour le rapport, l'introduction d'une queue asynchrone pour absorber des volumes plus importants, et la distribution par email planifiée.
